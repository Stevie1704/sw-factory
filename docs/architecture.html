Software Factory — Architecture Building Blocks

The software factory turns an explicitly authorized GitHub issue into a supervised, review-ready pull request while keeping workflow authority in a deterministic coordinator. This page maps the code that does it.

module github.com/Stevie1704/sw-factory Go 1.25.0 3 commands 18 internal packages ~73k lines of Go, tests included

01Overview

The factory is a host-local Go program. One operator runs it against one registered repository. It claims an authorized issue, freezes a specification packet, and then drives that work through fixed workflow stages. Interactive coding harnesses do the craft; the factory keeps every decision.

Three architectural rules explain most of the code shape:

  1. The coordinator owns workflow authority. Roles, stages, prompts, and transitions are declared in internal/workflow and compiled into the binary. Repository configuration selects policy inside those declarations; it can never add a stage or move authority.
  2. Every external system sits behind a narrow seam. Docker, cmux, Git, the GitHub CLI, and the harnesses are adapters. Coordinator code never sees a container name, a pane identifier, or a gh argument.
  3. Every external mutation is journaled before it happens. A durable pending-effect record lets a restarted coordinator tell "not done" from "done but unrecorded", so recovery never guesses.

Vocabulary. This page uses the glossary in CONTEXT.md exactly: run, invocation, checkpoint, gate, surface, worker, effect, specification packet. Read that file first when a term here is unfamiliar.

02System context

The factory is one host process plus the things it drives. Nothing runs in the cloud, and no data leaves the workstation except the GitHub writes the operator authorized.

A seam is an interface the coordinator depends on and an adapter implements. Each one hides a vocabulary the coordinator must never learn.

Optional capability interfaces are used throughout instead of one wide interface. RemoteBranchInspector, AncestryInspector, SurfaceReader, NativeSessionSnapshotProvider, ClaudeCredentialSeeder, and CleanupRuntime are each discovered with a type assertion. An adapter that cannot do the extra thing keeps working; the coordinator simply loses that recovery path and says so.

6.3 Unattended progression

One progression pass drives a claimed run as far as it can go without an operator running a stage command, then stops at the first human or infrastructure waiting state. The set of actions is closed, so a new transition cannot be added by accident.

ActionDoes
run_baselineEvaluates the frozen pre-edit gate suite.
start_agentLaunches the role the registry selects for the current stage.
accept_agent_reportValidates and accepts one invocation's structured report.
create_draft_pull_requestCheckpoints, gates, pushes, and creates or updates the draft pull request.
start_review_roundLaunches both review roles concurrently.
retry_review_readinessRetries the final readiness transition after a recoverable failure.

A pass reports why it stopped: idle, invocation_active, waiting, draft_pull_request, terminal, or unsupported. It is bounded at 32 steps, because a healthy run needs only a handful of transitions between two harness invocations — more than that is a coordinator defect, not ordinary work. Each pass also applies the structured commands an operator left on the issue or draft pull request, so no comment needs a separate polling command.

The test objection cycle is gated twice. It requires test_policy.allow_automated_objections, which stays false until the measured pilot records a proceed decision, and an accepted revision must still pass independent red verification before implementation resumes.

Concurrent applicable reviews form one human repair packet. Every packet records the maintainer surface and the event identity that produced it, and a review watermark makes repeated polling and a coordinator restart unable to apply the same review twice.

07Durability and recovery

The coordinator is a long-lived process that can be stopped at any instant, including between "I called GitHub" and "I recorded the answer". The durability design exists for exactly that instant.

The operational store

One host-local SQLite file, opened through modernc.org/sqlite, so the factory needs no cgo and the store stays a plain file the operator can copy. Schema version 35.

Every mutation the coordinator makes outside its own process is reserved before it is attempted and cleared after it is recorded. The reservation carries a stable identity, so a restarted coordinator asks a precise question — "did this effect happen?" — instead of retrying blindly.

Three recovery concepts, kept apart

Recovery diagnosis
A read-only comparison of one persisted non-terminal run with its registered repository, worktree, Git projection, and GitHub projections. It changes nothing. internal/factory/recovery.go.
Reconciliation
The restart pass that consumes one durable pending effect when safe, repairs the projections that effect owns, and otherwise pauses the run with a typed discrepancy. It may recreate a missing worker from the frozen invocation identity and permits one coordinator-owned native harness resume.
Recovery-required result
The typed result that reports the agreement state and the discovered discrepancies. Journaled runs reconcile safe effects automatically; unresolved disagreement pauses for a human. Legacy stores that predate the journal keep the fail-closed refusal.

Exactly-once, three ways

RiskMechanism
Two coordinators write the same runCompare-and-set on the run's monotonic Revision, plus a single-coordinator lock. A lost update surfaces as ErrRevisionConflict.
The same comment is applied twiceA processed-comment watermark on the run.
The same human review is applied twiceA review watermark holding the immutable GitHub review identity.
The same effect is applied twiceThe pending-effect journal, keyed by sha256(runID \0 kind \0 identity).
A same-process command looks like a restartService.startedInvocations records what this process launched, so a repeated command is rejected instead of being mistaken for recovery.
A notification fires twiceClaim and release rows in lifecycle_notifications.

08Worker anatomy

A worker is the only place agent-authored code runs. It exposes the run worktree, read-only Git metadata, explicitly declared repository caches, and factory-managed credential copies — nothing else.

PathAccessContains
/workread-writeThe run worktree. The working directory for every command.
/gitread-onlyGit metadata, so a role can read history but cannot rewrite the repository.
/invocationread-onlyThe frozen invocation packet: specification, role identity, and any frozen role craft with its source identity.

Isolation

  • Fixed non-root identity 10001:10001. Root is used only for the narrow credential-seeding step, never for a role command.
  • --cap-drop ALL and --security-opt no-new-privileges.
  • The image is pinned by sha256 digest in factory.yaml, and the digest is recorded on the run.
  • Mounts are a contract. MountContractStatus compares the running container against the start request and reports only booleans, so a stale-mount check never leaks a host path.

Environment policy

Two values, both declared: clean gives a command no inherited environment, and role additionally identifies the workflow role that owns the invocation. Repository configuration selects the policy for setup and for each gate. This repository uses clean everywhere.

Credentials

Each harness reads its credential through a symbolic link in its own role home — $HOME/.codex/auth.json and $HOME/.claude/claude-credentials.json — pointing into the shared credential volume. The two harnesses share one volume and never share a file. The host harness directory is never mounted, because that would give a role the operator's own session state. factory auth reseeds one credential from its host source without modifying that source.

Skills

The worker image bakes the curated skill set into both role homes, so the agent-visible instruction set is pinned by the image digest rather than inherited from a personal host directory. The embedded role prompts scope which skills each role may use. See ADR 0006.

09Cross-cutting concerns

Startup diagnosis

Every subsystem owns its own checks in a doctor.go beside its implementation. internal/doctor only runs them and reports. Eight packages contribute: config, git, github, harness, store, terminal, worker, and factory which composes the rest.

Three properties make this useful rather than decorative:

  • Checks run after a failure too, so factory doctor reports every problem in one pass instead of one problem per run.
  • Problem and Action are separate required fields. A failure that cannot say how to fix itself is not a finished check.
  • Results are bounded. A check never returns raw process output, so a diagnosis cannot leak a credential or a transcript.

Coverage includes host configuration, external access, the repository, the terminal, the worker, the harness, authentication, and operational-store readiness — plus one independent target-branch resolution check for every configured role_craft entry, so a misconfigured craft path fails at startup and not mid-run.

The trust model

Three kinds of text reach a role, and their authority is strictly ordered.

LayerOwnerCanCannot
Authority sectionfactory, compiled in Declare role ownership, permitted paths, workflow-stage boundaries, safety rules, report contracts. Be replaced or overridden by anything.
Craft sectionfactory, replaceable via role_craft Advise how to do the work. Selected bytes are frozen at claim with their SHA-256 identity. Widen the frozen specification, move a stage, change permitted paths, or alter the report contract.
Repository guidancethe repository, read from the base checkpoint Explain repository conventions. An empty guidance set is valid. Redefine factory ownership, workflow stages, safety rules, or report contracts. It is untrusted input.

Both craft and guidance are read from an exact commit, never from a live checkout, so an edit made during a run cannot change what a role was given. See ADR 0007.

Two-axis review

Specification review and documented-standards review are separate concurrent axes with separate durable findings and separate statuses. They are not two opinions merged into one verdict.

AxisJudgesCan block on
spec_reviewWhether the exact-base-to-checkpoint diff satisfies the frozen specification.A concrete correctness, security, or specification violation.
standards_reviewWhether the diff follows this repository's documented rules.Only a concrete violation of a named repository rule. A heuristic baseline finding is advisory and cannot block.

Every review invocation mounts the exact base-to-checkpoint diff as the regular read-only /invocation/review.diff file beside specification.json, including a zero-byte artifact. review_context records its stable worker path, byte count, and SHA-256 identity. Reviewers page it with bounded line windows and line-numbered search; restart recovery requires a regular file matching the recorded size and identity and fails closed on a discrepancy. See ADR 0005.

Privacy and evaluation

The factory prohibits outbound telemetry. What it keeps instead is a content-free local evaluation summary: run outcomes, effort, escalations, and human dispositions, with no prompts, transcripts, diffs, source contents, logs, or credentials. Outcomes are the same closed set as run status. Deletion is an explicit operator command, never a background sweep. See ADR 0001.

The same boundary shapes error handling. A harness launch failure captures at most 200 lines of its surface for local diagnosis, and that transcript is deliberately absent from Error(), because launch errors reach operator-visible projections such as the run lifecycle reason and the GitHub status comment, which must stay free of work content.

Bounded content, everywhere

Nothing that crosses a boundary is unbounded. The report envelope caps at 256 KiB with per-field rune and count ceilings. A progression pass caps at 32 steps. Native session discovery caps at 60 seconds. Repair loops cap at their declared retry_limits. A ceiling that is hit is a reported state, not a silent truncation.

Testing seams

Roughly half the tree is tests, and the seams exist partly to make them cheap. Every host adapter takes an injectable CommandRunner, so a contract test never launches the real git, gh, docker, or cmux. workflow.NewRegistry is exported specifically so the extensibility seam can be tested with declarations that are not the default. Factory.Dependencies.StartupDiagnosis is injectable so polling tests stay deterministic. worker/skills_contract_test.go keeps the baked skill set and its documentation in agreement.
